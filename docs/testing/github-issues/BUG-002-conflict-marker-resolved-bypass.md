## 问题

合并冲突已由 Grove 解决并刷新后，若外部进程再次写入完整冲突标记块，冲突文件视图下方的快捷「标记为已解决」入口不会重新检查磁盘内容。点击该入口会在没有警告的情况下把仍含完整冲突块的文件暂存为已解决，随后可以继续并提交含冲突标记的合并提交。

这是一个有明确前置条件的保护缺口：常规顶部冲突标记入口在相同完整标记内容下会重新检查并弹出警告。早先仅用孤立、不完整标记行进行的测试结论已撤回，不属于本问题的证据或复现步骤。

## 环境与前置

- Grove 3.0.0（9），macOS 27.0.1，arm64。
- 本地合成 Git 仓库。分支 `qa-marker-guard` 从 `55993c6decde3743ffa4c760956361b35fb08dfc` 开始，与 `main`（`2a9266b449597e8a9acdf1e8994499bfa6e85b85`）存在 `base.txt` 冲突。
- 一次完整 GUI 定向复现；另有正常顶部入口对完整冲突块的保护对照。

## 逐步复现

1. 在合成仓库合并 `main`，确认 `base.txt` 处于 UU 冲突。初始完整冲突块通过 Grove 顶部常规冲突标记入口检查时出现警告；取消警告，保持冲突状态。
2. 在 Grove 冲突视图点「采用当前更改」，解决当前冲突块。
3. 从外部向 `base.txt` 追加普通文本「外部解决补充行」。在 Grove 冲突文件视图点击「刷新」，使界面进入“文件里没有冲突标记”的状态，并显示下方快捷「标记为已解决」入口。
4. 在不刷新 Grove 的情况下，从外部向文件追加完整块：`<<<<<<< external-full-block`、`外部当前内容`、`=======`、`外部传入内容`、`>>>>>>> external-full-block`。CLI `git diff --check` 能识别三处残留冲突标记。
5. 点击冲突视图下方快捷「标记为已解决」按钮（不是顶部常规冲突标记入口）。
6. 在 Grove 点「继续」完成合并，并检查提交及提交内容。

## 预期与实际

- 预期：所有「标记为已解决」入口都重新读取当前文件并使用一致的冲突标记保护。检测到完整冲突块时应明确警告，且仅在用户明确选择仍然保留标记后才允许继续；正常消除冲突标记的路径应可顺利完成合并。
- 实际：下方快捷入口没有警告，直接显示冲突已解决并把含完整冲突块的文件暂存。点击「继续」生成合并提交 `f3b337ad71cb2403086a4f8324319292e98df211`，双亲为 `55993c6decde3743ffa4c760956361b35fb08dfc` 与 `2a9266b449597e8a9acdf1e8994499bfa6e85b85`。`git show HEAD:base.txt` 确认提交内容保留完整冲突块；`git diff --check HEAD^1 HEAD` 报告三处 leftover conflict marker。
- 对照：顶部常规入口对文件内完整冲突标记显示警告「文件里还有 1 处冲突标记」，并提供「仍然标记为已解决」与「取消」。因此本问题只涉及下方快捷入口在已刷新后外部再次写入内容的路径，不代表所有冲突标记入口都无保护。

## 严重程度

S3。该路径可能把未解决的冲突块静默带入一条正常双亲合并提交；需要外部修改发生在视图刷新之后并使用下方快捷入口。已有顶部常规入口仍提供保护。

## 修复验收

1. 上方常规入口与无标记状态下方快捷入口都重新读取文件，并对完整冲突标记执行一致的警告保护。
2. 刷新后由外部写入完整冲突块，再点下方快捷入口，应警告而非静默暂存；只有明确确认后才能按产品定义继续。
3. 正常采用一侧或编辑删除冲突标记后，仍能标记解决并完成双亲合并提交。

## 复核历史

早期误报只追加了孤立的 `<<<<<<<` 或 `>>>>>>>` 行，且当时仅验证暂存，没有验证提交；该原判定已经撤回。此处新问题由完整冲突块、上下入口区分及真实合并提交证据支持。历史撤回正文副本：`dist/qa/20261020/deep/codex-20261021/issue12-withdrawn-body-before-narrow-repro.md`。
