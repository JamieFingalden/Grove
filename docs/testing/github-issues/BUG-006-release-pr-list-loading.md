## 问题

用户实机发现“全部 PR”远慢于“开放”；本轮在签名 Release App 3.0.0（9）中确认会永久停在加载中，已知仓库实际有 10 条历史 PR。

## 复现

1. 打开 Grove 仓库的项目评审页，“开放”正常显示空列表。
2. 点击“查看全部”或筛选“全部”。
3. 请求子进程结束后，列表仍显示“正在加载 Pull Request…”，手动刷新也不恢复。

## 判据

- 同仓库只读 CLI 全部查询约 3.953 秒，返回 10 条；开放约 2.120 秒，返回 0 条。网络确有差异，但不能解释永久加载。
- App 临时状态日志：请求为 all，两个并发返回结果却均标记为 open，编号、origin、筛选校验都通过；结束时条数 0、hasLoadedPullRequests=false。
- 发布优化配置运行原有 `PullRequestLoadStateTests` 可复现；Debug 的历史测试结果不足以覆盖该发布行为。

## 修复

在 RepositoryModel 的并发列表任务中明确捕获筛选值，先 await 获取请求列表，再组装带筛选标识的返回结果。保留列表与侧栏开放计数分别发布的机制。

本地详细记录与验证结论见 docs/testing/PR_PERFORMANCE_2026-10-21.md；实机截图、状态追踪和前后 Release 测试日志保存在 dist/qa/20261021/pr-performance/。临时诊断代码在交付前移除，源码不提交。

## 本地验收结果

6 项 Release 定向测试全部通过。移除诊断后重建的最终 App 已真实验证开放、全部（10 条）、已合并（8 条）、已关闭均可完成加载。当前仅交付 dist/Grove.app；二进制 SHA-256 为 81f3018f1c00a4b8a9c1134f17e935290ea6825e57c9a68dde1d7df9c80898cf。本地修复未提交，Issue 保持开放供后续代码交付跟踪。
